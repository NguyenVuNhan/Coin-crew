# Nx workspace and by-kind libraries — design

Date: 2026-11-02 · Branch: `NguyenVuNhan/Nx-workspace` · Status: approved 2026-11-03

## 1. Why

Nothing is broken today. CoinCrew is about to grow well beyond group splitting (see the owner's roadmap: phase 2 Google Sheets export + Gemini, phase 3 personal money records in the style of Money Lover plus QR pay, Apple Pay capture and bank-email capture, phase 4 investments and imports). Today almost the whole front end lives in one package (`packages/web-common`: 26 screens, ~95 components, helpers, API client, platform bridge, i18n, theme), and the API is one Worker whose route folders all lean on the same database, helper and sign-in code.

The owner wants structure in place **before** those features land: an Nx workspace with libraries split **by kind** (design system, data access, platform, i18n, helpers, database, auth…) so new features have an obvious home and can reuse what exists. Fencing off each feature area (trips, payments, people…) into its own library is **not** the goal of this migration.

## 2. Goals, non-goals, anti-goals

**Goals**
- Nx manages the repo: cached tasks, a project graph, "only what changed" in CI.
- The front end and the API are split into by-kind libraries (§5, §6) with enforced import rules (§7).
- The package scope changes from `@fsl` to `@cc` everywhere (§4).
- Everyday commands keep working as typed today (§8).

**Non-goals**
- No per-feature libraries (trips, payments, people…) yet. Screens stay together in one library.
- No new features, no UI changes, no dependency upgrades beyond what Nx itself needs.
- No Nx Cloud / remote cache.
- No general linting. ESLint is added for the Nx module-boundary rule and the `zmp-sdk` import restriction only (§7).
- No change to which TypeScript checks the code: every `tsc` in every script stays TypeScript 7. TypeScript 6 is added only as the API that tools load (§8).
- Moving the API route handlers into libraries. They stay in `apps/api`.

**Anti-goal (the owner's words: "the application stops working")**
Structure changes, logic and behaviour do not. Every screen, flow, API response, stored value, URL, cookie, deploy and build output behaves exactly as before. A move that needs a logic change to work is the wrong move; find another split or leave the file where it is.

Concretely this means:
- Code is **moved and re-imported**, not rewritten. The only edits allowed in moved files are import specifiers, path strings that point at moved files, and comments that name old paths/packages.
- Existing tests keep their assertions unchanged. They may be moved to another library and have their imports/paths updated; nothing else. **The total number of tests per suite before and after must match** (record the counts first).
- These names contain "fsl" but are not the `@fsl` scope and **must not change**: the `fsl-*` CSS classes tests select by, the D1 database name `fsl` (live in production), the `fsl_lang` localStorage key, and any other stored key, cookie name or URL.

- App names: `@cc/api`, `@cc/web`, `@cc/zalo`, `@cc/zalo-relay`.
- Library names: §5, §6.
- **Not renamed:** dated specs and plans in `docs/superpowers/` stay as written; they are history. (Planner's call.)
- The stray, committed `apps/web/tsconfig.tsbuildinfo` is deleted and `*.tsbuildinfo` added to `.gitignore`. (Planner's call.)

**Workers Builds (owner action, needed before merge):** change the dashboard build command to `npm run build -w apps/web` and the deploy command to `npm run deploy -w apps/api`. The folder form works with both the old and the new code, so it can be switched any time before merging. The apps do not move folders, so these paths stay valid. The spec's README/setup docs must show these folder-form commands.

## 5. Front-end libraries

New top-level folder `libs/`. `packages/` disappears.

| Library | Folder | Holds | May import |
|---|---|---|---|
| `@cc/core` | `libs/shared/core` | today's `packages/core`, unchanged | nothing internal |
| `@cc/web-i18n` | `libs/web/i18n` | `i18n/` (`en`, `vi`, `t`, `setLang`, language store) | core |
| `@cc/web-util` | `libs/web/util` | helpers with no React UI, no API calls, no platform: e.g. `time`, `nameSearch`, `clipboard`, `media`, `linkTokens`, `qr` and similar from `lib/` | core, i18n |
| `@cc/web-ui` | `libs/web/ui` | the design system: shadcn `components/ui/*`, `lib/utils` (`cn`), `styles/globals.css` (the theme), and the app wrappers named in `CLAUDE.md` (`Button`, `Sheet`, `Modal`, `Pill`, `Avatar`, `Skeleton`, `InlineError`, `Snackbar`, icons, `Amount`) plus other components that know nothing about CoinCrew concepts | core, i18n, util |
| `@cc/web-platform` | `libs/web/platform` | `platform/` (`PlatformProvider`, `usePlatform`, `browserPlatform`, bridge types, `session` store) | core, util |
| `@cc/web-data-access` | `libs/web/data-access` | `api/` (client, React Query hooks) and `platform/zaloSession.ts` (it calls the API; moving it here breaks the platform ↔ api cycle) | core, util, i18n, platform |
| `@cc/web-screens` | `libs/web/screens` | everything else from `web-common`: `screens/`, CoinCrew-specific components (`ExpenseRow`, `BalanceCard`, `SignInButtons`, …), `lib/` hooks and helpers that use the API or domain text (`tripBase`, `tripText`, `useTripAction`, `navHistory`, …), `App`, `AppRoot`/`bootApp`, `config`, `assets/` | everything above |

Rules for placing a file:
- A file goes in the **lowest** library whose allowed imports cover everything it imports. If that would need a logic change, it goes higher (worst case it stays in `web-screens`).
- "Knows nothing about CoinCrew concepts" for `web-ui` means: it doesn't use trips, expenses, people, payments, groups or the API. When in doubt, it stays in `web-screens`.
- The exact file-by-file mapping is the builder's, following these rules. The table's examples are guidance, not a contract; verify each file's imports.

Public surface:
- Each library's `package.json` `exports` point at raw `.ts` source, like today. `@cc/web-ui` also exports `./styles.css` (the theme).
- `@cc/web-screens` keeps today's `web-common` root exports (`AppRoot`, `bootApp`, `PlatformProvider`, `usePlatform`, `browserPlatform`, `sessionStore`, `PlatformBridge`, `ShareCard`, `ZaloFriend`) so `apps/web` and `apps/zalo` change only their package names. Re-exporting platform symbols from `web-screens` is acceptable for this migration; `apps/zalo` importing the types straight from `@cc/web-platform` is also fine (builder's call).
- The shells import the theme from `@cc/web-ui/styles.css`.
- `globals.css` has `@source "..";` (scan web-common for classes). After the move it must cover **every** web library that uses Tailwind classes (e.g. `@source "../../../";` relative to `libs/web/ui/src/styles`, or one `@source` per library), or classes silently disappear from the build. Proof: the built CSS of `apps/web` contains the same set of selectors before and after (compare the generated CSS files' selector lists). (Planner's call.)

shadcn:
- `npx shadcn@latest add <name>` must keep working and land new components in `libs/web/ui`. Use shadcn's monorepo setup: `components.json` aliases point at the package (`@cc/web-ui/components/ui`, `@cc/web-ui/lib/utils`, …) and `@cc/web-ui`'s `package.json` `exports` expose those subpaths. **The `@/` alias is removed everywhere** (tsconfig `paths`, Vite and Vitest `resolve.alias`): Nx only sees `paths` in the root tsconfig, so a per-project `@/` import would be an edge invisible to the boundary check (§7), and the shells' global Vite `@` alias can only point at one library anyway. Every `@/…` import becomes a relative import (inside `web-ui`) or an `@cc/web-ui/...` import (elsewhere).
- Prove it by running `npx shadcn@latest add <an already-installed component> --dry-run` (or the equivalent that writes nothing) from the new location.

Tests:
- Each library gets its own `vitest.config.ts` (jsdom where React is involved) and `test`/`typecheck` targets.
- A test lives in the lowest library where everything it imports is allowed. Many tests in today's `src/test/` and `screens/__tests__` render full screens; they stay in `web-screens`.
- Shared test helpers (`test/render.tsx`, `fixtures`, `fundFixtures`, `fakePlatform`, `media`, `setup.ts`) go where their imports are allowed. If lower libraries' tests need them, put them in a test-only library `libs/web/testing` (`@cc/web-testing`, tag `type:testing`) that only test files may import. Builder's call whether that library is needed.
- The `maxWorkers: 2` setting and its comment carry over to every jsdom Vitest config (it prevents worker crashes on the owner's Windows machine).
- `style-guard.test.ts` and `ui-components-guard.test.ts` keep their assertions but must walk **all** web library sources together (not one library), so "globals.css is the only stylesheet", "no raw hex", the `>100 files` sanity check and the canvas-painter exemption (`qr.ts`, now under `web-util`) still hold across the whole front end. Updating their walk root/paths is allowed; changing what they assert is not.
- `apps/zalo/src/__tests__/no-sdk-in-web.test.ts` keeps working against the web build output.

## 7. Import rules

Every project gets two tags:
- **scope:** `scope:shared` (core), `scope:web` (web libraries, `apps/web`, `apps/zalo`), `scope:api` (api libraries, `apps/api`), `scope:relay` (`apps/zalo-relay`).
- **type:** `type:app`, `type:screens`, `type:data-access`, `type:platform`, `type:ui`, `type:i18n`, `type:util`, `type:testing` (if created).

Constraints:
- `scope:web` → `scope:web`, `scope:shared`. `scope:api` → `scope:api`, `scope:shared`. `scope:shared` → `scope:shared`. `scope:relay` → nothing internal. The front end can never import back-end libraries and vice versa; `@cc/core` remains the only shared contract (`api-types.ts`).
- Type rules follow the "May import" columns in §5 and §6. `type:testing` may be imported only from test files.
- `zmp-sdk` may only be imported by `apps/zalo` (enforced by the boundary check below, alongside the existing `no-sdk-in-web` test).

**How it is enforced** (verified by a spike on 2026-11-03 with the §8 TypeScript setup, Nx 24.0.3, ESLint 10.14, typescript-eslint 8.72.1; 490 files parse cleanly):
- Root `eslint.config.mjs` (flat config) with the typescript-eslint parser for `.ts`/`.tsx`, running **only** `@nx/enforce-module-boundaries` (the depConstraints above, from tags in each project's `package.json` `"nx": { "tags": [...] }`) and `no-restricted-imports` for `zmp-sdk` / `zmp-sdk/*` outside `apps/zalo`.
- `type:testing` (if `@cc/web-testing` exists): non-test files may not import it; an override block for test files (`**/*.test.ts(x)`, `**/__tests__/**`, `**/test/**`) allows it. The spike proved this per-file split works.
- **Lint only through Nx** (`nx run-many -t lint`, `nx affected -t lint`, root `npm run lint`). The boundary rule reads Nx's *cached* project graph; plain `npx eslint .` with no or a stale cache prints "No cached ProjectGraph… rule will be skipped" and **exits 0**. Running via Nx builds the graph first. CI and docs must never call bare `eslint` for this check.
- `libs/web/screens/.../navHistory.tsx` (today `packages/web-common/src/lib/navHistory.tsx:209`) has an `eslint-disable-next-line react-hooks/exhaustive-deps` comment for a rule that isn't installed; ESLint reports it as an unknown rule. Delete that comment line (a comment-only change). (Planner's call; installing `eslint-plugin-react-hooks` would be general linting.)
- The spike caught injected violations: bare, relative (reported as "must begin with a npm scope") and `import type` cross-project imports, a cross-scope import, and `zmp-sdk` in web-common; `zmp-sdk` in `apps/zalo` was allowed.

The migration must finish with zero violations, without suppressions.

## 8. Nx setup and commands

- Current stable Nx, installed with npm into the existing npm workspaces. npm, the single lockfile and `node_modules` layout stay. Libraries stay workspace packages (each with a `package.json`); no `tsconfig` `paths` mapping is introduced. (Planner's call: this matches how the repo already resolves packages.)

**TypeScript 6 + 7 side by side** (Nx's documented setup, https://nx.dev/docs/kb/typescript-7; verified by a spike on 2026-11-03). TypeScript 7 ships no JS compiler API, which Nx's graph code, typescript-eslint and `@nx/eslint` need. Root `package.json` devDependencies get exactly:
```json
"@typescript/native": "npm:typescript@^7.0.2",
"typescript": "npm:@typescript/typescript6@^6.0.2"
```
- `tsc` (in every workspace and script) is TypeScript 7 — the spike confirmed `npm exec -w <each> -- tsc --version` → 7.0.2, including after `npm ci` from a clean copy. `tsc6` is TypeScript 6; `require('typescript')` is 6.x. **No script changes.** Every project tsconfig already passes under `tsc6 --noEmit`.
- `tsconfig.base.json` keeps its name.
- Proof to keep in the plan: after install, `npx tsc --version` → 7.x and `node -p "require('typescript').version"` → 6.x; record both in the PR.
- Known side effects (accepted): ~200 more packages (Nx, ESLint, Babel); `@nx/eslint` nests its own TypeScript 6.0.3; VS Code users who pick "workspace TypeScript" must point it at `node_modules/@typescript/old/lib` (note this in the README). Drop the TypeScript 6 alias once TypeScript 7 ships its API.

**Targets and plugins:**
- `test`, `typecheck`, `build`, `dev` and the app-specific scripts (`deploy`, `deploy:testing`, `deploy:tunnel`, `db:migrate:remote`, `e2e:server`, `start`) come from **package.json scripts**.
- Register only `@nx/eslint/plugin` (infers a cached `lint` target per project). Do **not** register `@nx/js/typescript` (it infers nothing the scripts don't already give), `@nx/vite/plugin` or `@nx/vitest` (`@nx/vite` loads every `vite.config.ts` while building the graph; `apps/zalo`'s throws without `VITE_API_ORIGIN`, which broke **every** Nx command in the spike, and it infers cached builds, which §8 forbids).
- `nx.json` must include:
  ```json
  "pluginsConfig": { "@nx/js": { "analyzeSourceFiles": true, "analyzePackageJson": true } },
  "namedInputs": {
    "sharedGlobals": ["{workspaceRoot}/tsconfig.base.json", "{workspaceRoot}/package.json", "{workspaceRoot}/package-lock.json", "{workspaceRoot}/eslint.config.mjs"],
    "default": ["{projectRoot}/**/*", "sharedGlobals"]
  },
  "targetDefaults": {
    "typecheck": { "cache": true, "inputs": ["default", "^default"] },
    "test": { "cache": true, "inputs": ["default", "^default"] },
    "lint": { "cache": true, "inputs": ["default", "^default"] }
  }
  ```
  `analyzeSourceFiles` makes Nx see imports written in source (an earlier spike showed an import with no `package.json` dependency is otherwise missed silently). `sharedGlobals` makes a root config change invalidate the cache (without it a spike got stale hits and an empty `affected`).
- `nx affected` has no `--dry-run` (it forwards the flag to the task); use `--graph=stdout` to preview.
- Spike measurements for reference: `nx run-many -t typecheck` 6/6 in ~5 s (31 ms from cache); `nx run-many -t lint` ~8 s cold; `nx run-many -t test --parallel=1` all green in ~7 min. Baseline test counts: core 295, web-common 1025, api 657, zalo-relay 12, zalo 14 + 1 (`no-sdk-in-web` runs only when a web build exists). Re-record them on the branch's starting commit.
- Caching on: `test`, `typecheck`, `lint`. Off: `build`, `dev`, `deploy*`, `db:*`, `e2e:server`, `start`. Builds are not cached because their output depends on things Nx can't see: the git SHA baked in as `__APP_VERSION__` and the untracked `.env` that sets `VITE_API_ORIGIN` for the Zalo build. (Planner's call.)
- Test parallelism: jsdom suites crash on the owner's Windows machine when too many workers run at once (`maxWorkers: 2` comment). Root `npm test` runs the `test` target with `--parallel=1` so Nx doesn't multiply the workers. (Planner's call.)
- `apps/zalo`'s `no-sdk-in-web` test keeps today's behaviour (skips when there is no web build); Nx gets no new dependency for it. The "done" check runs it after a build explicitly (§11).
- Where CI builds `@cc/zalo`, it sets `VITE_API_ORIGIN` to a placeholder (`https://example.invalid`); nothing built in CI is deployed.
- `typecheck` and `test` of a project depend on nothing being built first (sources are raw `.ts`). `e2e` depends on `@cc/web:build`.
- `.nx/` cache folders are git-ignored.

Commands that must keep working exactly as typed (they may run Nx underneath):
- Root: `npm run dev`, `npm test`, `npm run typecheck`, `npm run e2e`, `npm run tunnel`. Add `npm run lint` (= `nx run-many -t lint`).
- Per project with npm's `-w` flag: `npm run build -w apps/web` (and `-w @cc/web`), `npm run deploy -w apps/api`, `npm run db:migrate:remote -w @cc/api`, `npm run e2e:server -w @cc/api`, `npm run deploy -w @cc/zalo` (and `deploy:testing`, `deploy:tunnel`), `npm test -w @cc/zalo-relay`.
- `docker build -f apps/zalo-relay/Dockerfile .` from the repo root.
