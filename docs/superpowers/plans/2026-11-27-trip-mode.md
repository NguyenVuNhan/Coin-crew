# Trip Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In this repo, implementer tasks run as Orca workers through the `gemini-execution` skill; the planner reviews every diff and runs the tests.

**Goal:** Trip mode (issue #158): a trip is a tag plus dates. While it runs (and for bookings before it), new expenses and the owner's shares from the trip's groups get the trip tag. A trip page shows what the trip cost, with an optional limit that is a #159 one-off budget.

**Architecture:**
- **Core logic.** Pure trip logic lives in `@cc/core` (`travels.ts`): which trip a date or a share belongs to, overlap, state, and the trip summary. The summary is built from the report engine's `listCountedSpending` rows, so a trip never counts money a second way.
- **Storage and API.** Trips are stored in three new D1 tables behind `requirePersonal`.
- **Share tags.** Group shares get their tag from a server **share tagger** that writes ordinary `personal_group_link_tags` rows plus a per-share mark. The browser calls it after the group copy syncs. Reports, budgets and lists then see the tags with no new read path, and nothing touches group write paths.
- **Own-expense tags.** The entry form adds the trip tag by name on save.

**Tech Stack:** TypeScript, Hono and Drizzle on Cloudflare D1 (vitest `cloudflare:test`), React 19 and React Query, Tailwind v4 with the shadcn wrappers, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-27-trip-mode-design.md`: decisions T1–T20, constraints §6, interaction flow §8. Mockups: `docs/superpowers/mockups/trip-mode/trip-flow.html` (the flow) and `trip-overview.html` (option A). The base branch is `feat/budgets` (PR #159); this branch already contains it.

- **Code name is `travel`** (`personal_travels`, `travelRoutes`, `TravelDef`, `/travels`), because `trips` already means a CoinCrew group. UI copy says "Chuyến đi" / "Trip". A group is "nhóm".
- Money is a whole number in the currency's smallest unit. Dates are local `YYYY-MM-DD`. "Today" comes from `todayLocal()` on the web and a `today` body or query field on the server, as budgets do.
- Every personal route uses `requirePersonal` and scopes by `user.id`. Unknown or foreign ids return 404.
- **Trip dates:** `countsFrom <= start <= end`. `countsFrom` defaults to `min(today, start)` (T2). Start→end ranges of two trips of one user never overlap (T12).
- Only `expense`-type own entries are tagged (T11). A share gets at most one trip's tag automatically (T7).

## Review Focus

1. **A trip created entirely in the past** (back from Đà Lạt, entering it afterwards):
   - its state is `done`;
   - the existing-expenses question lists everything in its dates;
   - the share tagger tags nothing until the owner says yes.

   → test in Task 4 (`creates a past trip and marks existing shares skipped`).
2. **A share the tagger already handled is later removed or re-dated in the group.** The mark stays, a missing row never crashes the tagger, and a share re-dated out of the range keeps its tag. → test in Task 5.
3. **Changing the date in the entry form across trip boundaries** (during → lead-up → outside → during):
   - the row switches between pre-filled, suggestion and hidden;
   - an explicit ✕ survives a date change that stays inside the trip;
   - editing an existing expense never adds the tag by itself.

   → test in Task 10.
4. **The trip's tag renamed or deleted from the tags screen:**
   - the trip's name follows a rename;
   - deleting the tag deletes the trip (cascade), and the Sổ chi tiêu row and `/travels/:id` handle it with no broken row;
   - the trip's budget is handled the way #159 handles a deleted tag.

   → tests in Task 4 and Task 9.
5. **The limit's currency differs from every row spent** (a ₫ limit, a trip spent only in ฿). The bar shows 0 of the limit, the page shows the ฿ total, and the "≈ ₫" line follows T16. Nothing divides by zero. → test in Task 2.

  ```ts
  export interface TravelDef {
    id: string; tagId: string; name: string;        // name = the tag's name
    start: string; end: string; countsFrom: string; // countsFrom <= start <= end
    groupIds: string[];                              // CoinCrew group (trips.id) ids
    budgetId: string | null;
  }
  export type TravelState = 'upcoming' | 'on' | 'done';
  export function travelState(t: TravelDef, today: string): TravelState; // on: start<=today<=end
  export type TravelMatch = { travel: TravelDef; mode: 'on' | 'leadup' };
  export function travelForDate(travels: TravelDef[], date: string): TravelMatch | null;

  export function travelDayIndex(t: TravelDef, today: string): { day: number; of: number } | null; // "ngày 2/3"
  export function daysUntil(t: TravelDef, today: string): number;
  ```
  - `travelForDate`: "on" when `start <= date <= end`. Otherwise "leadup" for a trip with `countsFrom <= date < start`; when several match, the one with the earliest `start`.
  - `travelForShare`: only trips whose `groupIds` include `share.tripId` and whose `countsFrom <= date <= end`. Prefer a trip whose `start <= date <= end`, then the earliest `start` (T7).

**Interfaces:**
- Consumes:
  - `resolveTags`: export it from `entries.ts`; its signature stays the same.
  - `commitPersonalWrite`, `loadCachedGroupRows`, `findTravelOverlap` and `defaultCountsFrom` (Task 1).
- Produces (api-types):
  ```ts
  export interface TravelView extends TravelDef { createdAt: string }
  export interface TravelsResponse { travels: TravelView[] }
  export interface TravelLimitInput { amount: number; currency: CurrencyCode }
  export interface CreateTravelInput { name: string; start: string; end: string; countsFrom?: string; groupIds: string[]; limit?: TravelLimitInput; today: string }
  export interface UpdateTravelInput { name?: string; start?: string; end?: string; countsFrom?: string; groupIds?: string[]; limit?: TravelLimitInput | null; endNow?: true; today: string }
  export interface TravelExisting { own: { count: number; totals: { currency: CurrencyCode; amount: number }[] }; shares: { count: number; total: number } }
  export interface TravelSavedResponse { travel: TravelView; existing: TravelExisting }
  export interface ApplyTravelExistingInput { tag: boolean }
  ```
  Routes:
  - `GET /me/personal/travels` → `TravelsResponse`, newest start first.
  - `POST /me/personal/travels` → 201 `TravelSavedResponse`.
  - `PATCH /me/personal/travels/:id` → 200 `TravelSavedResponse`.
  - `DELETE /me/personal/travels/:id` → 204. It also deletes the linked budget (T20). The tag and existing tags stay.
  - `POST /me/personal/travels/:id/existing` (body `ApplyTravelExistingInput`) → 200 `{ tagged: number }`.

  Rules:
  - **Name and tag:** create resolves the name to a tag with `resolveTags`, reusing an existing tag (T1). PATCH `name` renames that tag, with 409 `TAG_TAKEN` when the name belongs to another tag.
  - **Validation:** 422 when `countsFrom > start` or `start > end`. 409 `TRAVEL_OVERLAP` with `{ details: { travelId, name, start, end } }` when start→end overlaps another trip.
  - **`endNow`:** sets `end = today`, and `start = today` if `start > today`.
  - **Limit:** `limit` on create creates a one-off tag budget over `countsFrom..end` through `budgetCreateStatements`, with `name` = trip name and the default excluded wallets (`defaultExcludedFor` logic: wallets marked not in reports). Store its id. Any change to dates moves that budget through `budgetMoveOnceStatements`. `limit: null` deletes it. A new `limit` on a trip without one creates it. A changed amount replaces the budget's single `personal_budget_limits` row (`effective_from = countsFrom`). A one-off budget has one period, so there is never a history to keep.
  - **Existing question (T10).** After create, or after a PATCH that changes dates or groups, the same batch writes `skipped` marks for every share that is in the trip's groups and `countsFrom..end`, has no mark yet, and has no trip tag yet. `existing` then counts:
    - own `expense` entries in `start..end` without the tag, totalled per wallet currency;
    - the shares just marked `skipped`, totalled from their `myShare` (`groupRowEffect(...).spending`).
  - **`POST …/existing { tag: true }`:**
    - inserts `personal_transaction_tags` for those own entries, bumping their `syncVersion`;
    - turns the trip's `skipped` marks into `tagged`;
    - upserts `personal_group_links` (`ON CONFLICT DO UPDATE SET sync_version = v, updated_at`; other fields untouched);
    - inserts the link tags.

    `{ tag: false }` does nothing and returns `{ tagged: 0 }`.
  - Every write goes through one `commitPersonalWrite` batch. Each route makes at most 50 queries.
